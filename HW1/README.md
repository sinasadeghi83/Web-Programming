# تمرین اول: آشنایی با Git — برنامه‌سازی وب

**نام:** سینا صادقی — **شماره دانشجویی:** 40131064
**درس:** برنامه‌سازی وب (مهندسی اینترنت)، دانشگاه صنعتی امیرکبیر — مهر ۱۴۰۵

---

## سؤال ۱: merge و rebase

**پاسخ:** هر دو دستور برای یکپارچه کردن تغییرات دو شاخه‌اند، اما به دو شیوه متفاوت.

- **`git merge`:** تاریخچه هر دو شاخه را حفظ می‌کند و یک *merge commit* تازه با دو والد می‌سازد (نوک شاخه جاری و نوک شاخه ادغام‌شونده). نتیجه تاریخچه غیرخطی و صادقانه است؛ ترتیب واقعی کار و نقطه اتصال شاخه‌ها در گراف دیده می‌شود.
- **`git rebase`:** کامیت‌های شاخه جاری را برمی‌دارد و یکی‌یکی روی نوک شاخه مقصد دوباره اعمال می‌کند؛ انگار از اول روی همان نوک کار شده بود. نتیجه تاریخچه کاملاً خطی و تمیز بدون merge commit اضافه است؛ اما شناسه (hash) کامیت‌های بازپخش‌شده عوض می‌شود، یعنی تاریخچه بازنویسی می‌شود.

**موقعیت مناسب merge:** ادغام شاخه قابلیت در شاخه مشترک `main` وقتی چند نفر روی آن کار کرده‌اند. چون بازنویسی تاریخچه مشترک خطرناک است، `merge` امن است و با merge commit مشخص می‌ماند چه چیزی، کی و از کدام شاخه وارد `main` شده.

**موقعیت مناسب rebase:** به‌روزرسانی شاخه شخصی و هنوز منتشرنشده (`push` نشده) با آخرین `main`، مثلاً قبل از باز کردن pull request با `git rebase main`؛ تاریخچه خطی و قابل‌مرور می‌ماند و چون شاخه هنوز به اشتراک گذاشته نشده، بازنویسی آن اشکالی ندارد.

## سؤال ۲: انتخاب بخشی از تغییرات

**پاسخ:** خروجی `git diff` تغییرات را به قطعه‌هایی به نام **hunk** تقسیم می‌کند؛ هر hunk یک بلوک پیوسته از خط‌های تغییرکرده به‌همراه چند خط زمینه (بدون تغییر) اطراف آن است تا جای تغییر مشخص باشد. سربرگ هر hunk (مثل `@@ -12,7 +12,9 @@`) شماره خط شروع و تعداد خط‌ها را در نسخه قدیم و جدید نشان می‌دهد.

استیج تعاملی با خط فرمان:

```bash
git add -p README.md
```

گیت تک‌تک hunkها را نشان می‌دهد و برای هر کدام می‌پرسد. گزینه‌های مهم: `y` (استیج این بخش)، `n` (رد)، `s` (شکستن hunk بزرگ به قطعه‌های کوچک‌تر)، `e` (ویرایش دستی خط‌ها)، `q` (خروج). با `git add -p` بدون نام فایل همین کار برای همه فایل‌ها انجام می‌شود.

**فایده:** وقتی در یک فایل دو کار نامرتبط انجام داده‌ایم، هر کدام را می‌توان در کامیت جداگانه و منسجم گذاشت. کامیت‌های کوچک و تک‌موضوعه، مرور، `revert` و `bisect` کردن آینده را بسیار آسان‌تر می‌کنند.

## سؤال ۳: یافتن منشأ خطا

**پاسخ:** `git bisect` با جست‌وجوی دودویی روی تاریخچه، اولین کامیت معیوب را در زمان لگاریتمی پیدا می‌کند.

```bash
git bisect start
git bisect bad HEAD        # نسخه فعلی خراب است
git bisect good v2.1       # نسخه v2.1 سالم بود
```

از اینجا گیت وسط بازه را checkout می‌کند؛ برنامه را تست می‌کنیم و اعلام می‌کنیم:

```bash
git bisect good   # اگر این نسخه سالم بود
# یا
git bisect bad    # اگر این نسخه هم خراب بود
```

با هر پاسخ نصف بازه حذف می‌شود تا گیت دقیقاً اولین کامیت معیوب را گزارش کند (به‌همراه نویسنده و تاریخ آن). در پایان حتماً:

```bash
git bisect reset
```

**مثال:** بین نسخه سالم انتشارشده و نسخه فعلی خراب، ۱۰۰ کامیت فاصله است. به‌جای تست دستی هر ۱۰۰ کامیت، با حدود ۷ مرحله (‎`log2(100) ≈ 7`‎) کامیت مقصر پیدا می‌شود. **چرا مفید است:** وقتی نمی‌دانیم کدام تغییر باعث خطا شده، bisect سیستماتیک و سریع مقصر را پیدا می‌کند؛ همچنین می‌توان تست را خودکار کرد (`git bisect run test.sh`) تا کل فرایند بدون دخالت دست انجام شود.

## سؤال ۴: بررسی تغییرات پیش از کامیت

فرض: `README.md` ردیابی‌شده و کامیت‌شده است؛ بخشی از تغییرات جدید استیج شده، سپس بدون `add` دوباره همان فایل ویرایش شده؛ پوشه `tmp/` هم فقط فایل موقت untracked دارد.

**پاسخ ۱ — دستورهای بررسی:**

```bash
git status          # نمای کلی: staged / unstaged / untracked
git diff            # تفاوت working tree با staging (ویرایش‌های جدید، واردنشده)
git diff --cached   # تفاوت staging با HEAD (آماده کامیت)
```

`git diff` ویرایش‌های دوم (بعد از آخرین add) و `git diff --cached` ویرایش‌های اول (استیج‌شده) را نشان می‌دهند؛ مکمل یکدیگرند.

**پاسخ ۲ — اثر کامیت معمولی بدون `-a`:** فقط بخشی از `README.md` که در staging است (ویرایش‌های اول) کامیت می‌شود. ویرایش‌های جدیدتر در working tree می‌مانند و فایل‌های `tmp/` چون untrackedاند اصلاً شرکت نمی‌کنند. **دلیل:** `commit` معمولی دقیقاً از روی اسنپ‌شات ناحیه staging ساخته می‌شود، نه فایل‌های روی دیسک. (گزینه `-a` هم فقط فایل‌های ردیابی‌شده را یک‌جا استیج و کامیت می‌کند و untrackedها را نادیده می‌گیرد.)

**پاسخ ۳ — جلوگیری از ورود `tmp/`:** در ریشه مخزن، فایل `.gitignore` با این خط:

```bash
tmp/
```

از این پس گیت این پوشه را در `git status` و `git add .` نادیده می‌گیرد. اما این برای فایلی که **قبلاً** ردیابی‌شده کافی **نیست**، چون `.gitignore` فقط روی untrackedها اثر دارد. برای خارج کردن فایل ردیابی‌شده از ردیابی (بدون حذف از دیسک):

```bash
git rm --cached <file>
```

## سؤال ۵: رفع merge conflict در کار گروهی

فرض: شروع از کامیت مشترک؛ شما در `feature-description` و هم‌تیمی در `main`، یک خط از `README.md` را به دو متن متفاوت تغییر داده و کامیت کرده‌اید؛ working tree تمیز است؛ هنگام merge شاخه شما در `main` روی آن خط conflict رخ می‌دهد.

**پاسخ ۱ — علت:** گیت هر تغییر را نسبت به جد مشترک (merge-base) می‌سنجد. چون **یک خط یکسان** در هر دو شاخه به دو شکل **متفاوت** تغییر کرده، گیت نمی‌تواند تصمیم بگیرد و به انسان واگذار می‌کند. اما هر تغییری در یک فایل لزوماً conflict نمی‌شود: تغییر بخش‌های متفاوت و دور از هم معمولاً خودکار ادغام می‌شود؛ conflict فقط وقتی رخ می‌دهد که تغییرات هم‌پوشان یا آن‌قدر نزدیک باشند که نتوان مطمئن بود مستقل‌اند.

**پاسخ ۲ — شناسایی:** فایل‌های درگیر با `git status` (بخش unmerged paths) مشخص می‌شوند. داخل فایل، دو نسخه با نشانگرها جدا می‌شوند:

```bash
<<<<<<< HEAD
متن نسخه main (مقصد)
=======
متن نسخه feature-description (ورودی)
>>>>>>> feature-description
```

بخش بالای `=======` نسخه شاخه جاری (HEAD یعنی main) و بخش پایین نسخه شاخه ادغام‌شونده است. با `git diff` هم همین نواحی دیده می‌شوند.

**پاسخ ۳ — مراحل رفع تا تکمیل:** فایل را باز می‌کنیم و متن نهایی را طوری می‌سازیم که **اطلاعات هر دو تغییر حفظ شود** و هر سه خط نشانگر را کاملاً پاک می‌کنیم. سپس:

```bash
git diff --check
grep -rn '<<<<<<<' . --exclude-dir=.git
```

اگر خروجی هر دو خالی بود، نشانگری نمانده است. حالا:

```bash
git add README.md
git status
git commit
git log --graph --oneline
```

**پاسخ ۴ — لغو merge در حال انجام:** اگر پیش از commit نهایی تصمیم بگیریم فعلاً نباید ادغام شود:

```bash
git merge --abort
```

شاخه جاری دقیقاً به وضعیت پیش از شروع merge (همان working tree تمیز) برمی‌گردد.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

(فرض: هنگام بازگردانی conflict رخ نمی‌دهد.)

**پاسخ ۱ — تغییر نخواسته و استیج‌نشده در `notes.txt`** (نسخه staging با HEAD یکسان؛ فقط این فایل، بقیه دست‌نخورده):

```bash
git restore notes.txt
```

فقط این فایل روی دیسک به حالت کامیت‌شده برمی‌گردد. (شکل قدیمی‌تر: `git checkout -- notes.txt`.)

**پاسخ ۲ — تغییر اشتباهاً استیج‌شده ولی کامیت‌نشده** (خروج از staging با حفظ ویرایش‌های working tree):

```bash
git restore --staged notes.txt
```

staging به HEAD برمی‌گردد ولی working tree دست‌نخورده می‌ماند. (شکل قدیمی‌تر: `git reset HEAD notes.txt`.)

**پاسخ ۳ — کامیت اشتباه pushشده در main مشترک** (هم‌تیمی‌ها pull کرده‌اند؛ working tree تمیز): اثر کامیت را با کامیت **جدید و معکوس** خنثی می‌کنیم، بدون حذف تاریخچه:

```bash
git revert <commit-hash>
```

`git revert` کامیت تازه‌ای می‌سازد که تغییرات کامیت اشتباه را برمی‌گرداند؛ تاریخچه فقط جلو می‌رود و مخزن هم‌تیمی‌ها با یک `pull` ساده به‌روز می‌شود. در مقابل، حذف کامیت از تاریخچه (`git reset --hard` + force push) در شاخه مشترک انتخاب بدی است: تاریخچه عمومی بازنویسی می‌شود، هم‌تیمی‌ها دچار واگرایی می‌شوند و ممکن است کارشان را گم کنند.
